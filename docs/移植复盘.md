# 原版 Firefly-RK3288 Android 17 移植复盘

日期：2026-11-07。我这次使用的是原版 Firefly-RK3288，配置为 2 GB RAM、16 GB eMMC，移植目标是 ARM32 / Android 17 API 37、Linux 6.18.60。我把移植中遇到的问题、原因、排查过程、最终处理和经验整理成这份独立复盘。文中的结论只覆盖这块板和实际做过的测试，不能直接推广到 Reload、Plus 或其他 RK3288 盒子。

## 先看结果

系统已能从 eMMC 启动并进入电视桌面，基础网络、USB 输入、H.264 硬解和 3.5 mm 音频已取得实际运行证据。我实际观看 YouTube 时，感觉流畅度明显改善，耳机声音也正常，但仍能察觉轻微卡顿。我决定先记录下来，留待后续优化，不能因此认为 YouTube 60 FPS 已完全解决。

HDMI 音频随后也完成了实际出声验证：换接支持音频的 32V3H-H6A 并修正外部设备模板地址后，我分别听到了 PCM1 左右声道测试、Android AudioTrack 测试和视频播放的声音。软件重启后的自动连接、只读挂载与 HDMI 路由的 192,000 帧播放进度也已通过；随后我在视频中拔出 HDMI、等 5 秒再插回，画面和声音都自动恢复，开发板没有重启。此前 DELL P2017H 无音频能力时保持模拟输出的负例仍保留；拔出期间的耳机回退、路由打开失败恢复和冷断电尚未验收。HEVC 自定义节点保持停用，VP9/AV1 硬解与 4K/8K 流畅播放没有完成验证。

本地原生解码测试中的 720 帧 1080p60 像素哈希全部正确；Surface 稳定窗口中间 8 秒达到 480/480 帧，更长 10 秒窗口为 597/600 帧。1080p30 的 360 帧测试零丢帧。这些结果不替代特定网络视频、特定播放器、长期运行和新整盘镜像完整重刷的验收。

## 第一部分：烧录、启动与网络
我根据这次工作目录中保留的日志、源码检查、工件清单和写后回读记录，回顾从首次 eMMC 写入到稳定进入 Android 的过程。这里记录的是原版 Firefly-RK3288、ARM32 Android 17 userdebug 移植和 Linux 6.18.60 系列构建；不代表 Reload、Plus 或其他 RK3288 产品已经验证。

**结论：没有一个“总开关”能解释全部故障。** 早期存在 Loader 地址映射错误；修正物理镜像后，又暴露定制 HEVC 初始化路径、ARM32 BPF 兼容性、缺失的网络内核功能、共享内存选择和图形服务所有权问题。各层分别需要独立验证。最终恢复启动的方案不等于完成 HEVC，也不等于完成全部视频性能优化。

证据路径均以原工作目录为根。原始证据中可能含设备身份、网络信息或本机路径，我只摘录经过筛选的技术事实，没有把原始日志整体复制到公开仓库。本部分根据当时留下的证据回顾，后续 HDMI 实装与重启验收另列。

### 2. 镜像大小、介质选择和最初的模型错误

**现象。** 我下载的文件只有约数百 MiB，解压和整盘烧录却需要 12 GiB，一开始并不理解为什么差这么多。我也想过像 PC BIOS 一样，直接指定从 TF 卡启动。

**原因与边界。** 镜像是包含分区表、文件系统和大量零填充空间的 raw 整盘镜像，压缩包大小并不是目标介质写入长度。本次镜像大小为 12,884,901,888 字节，512 字节扇区共 25,165,824 个，实际 eMMC 用户区必须容得下。它不是 Rockchip `update.img`，也不是 Android 标准头格式的单独 `boot.img`。

RK3288 BootROM 的板级流程与 PC BIOS 菜单不同。已核查的 RK3288 TRM 流程中，有效 eMMC ID BLOCK 位于 SDMMC 卡之前；写对 TF 的 IDB 位置，不会改变 BootROM 的顺序。已经取得执行权的 U-Boot 可以自行选择后续介质，但这是另一个阶段。Recovery/Maskrom 是下载恢复入口，不能当作“强制 TF”按钮。本文的最终硬件验收在 eMMC 路径上，不应据此给 TF 首启加上“已验证”标签。

**错误路线。** 把泛化的“TF 优先”经验套用到本板，或认为 Android 设备树禁用 eMMC 就能影响更早的 ROM，都不能成立。介质 IDB、RAM 下载包和整盘镜像也不能仅凭 `.bin`/`.img` 扩展名互换。

**经验。** 发放镜像时同时注明压缩大小、展开大小、镜像类型、板型、最小实际容量和已验收的启动介质。

证据：`outputs/Firefly-RK3288-TV/原始文档/boot-selection.md`；`outputs/Firefly-RK3288-TV/records/emmc-install-source-audit.json`；`work/fastboot-persistence-audit/REPORT.md`。

### 3. eMMC 写入成功却冷启动仍进旧 Loader

**现象。** 我给开发板上电后，发现所有指示灯都不亮，HDMI 也没有信号。我完全断电、拔掉 TF 卡，不按 Recovery 正常上电后，USB 仍显示 LOADER。烧录工具此前出现过下载完成和校验成功的提示；前 16 MiB 的某些导出甚至与目标镜像完全相同。

**确证原因。** 后来独立 RAM usbplug 的物理读回显示：物理前 4 MiB 仍有旧 GPT 和五份旧 IDB，而物理 4 MiB 起的连续 12 MiB 与新镜像前 12 MiB 逐字节相同。旧 Loader 对读、写共同附加 `0x2000` 个扇区，也就是 4 MiB。写入与回读都经过同一错误映射时，内容相等仍然可以成立，因而“回读一致”没有自动证明物理 LBA 起点正确。

串口进一步确认冷启动执行 `DDR Version 1.00 20160530` 和旧 `U-Boot 2014.10-RK3288-10`，而不是目标 U-Boot 2024.01。旧引导无法找到有效参数和预期分区，主动进入 Rockusb。LOADER 这个 UI 标签只能说明 USB 模式，不能识别运行的是哪份引导代码。

**排查与错误路线。**

- 最初将 Loader 空间中的前 16 MiB 一致解释为物理启动区正确，后续证据推翻了这一解释，记录中明确撤回。
- 再次用 GUI 的 13 分段流程写入并导出，仍未改变物理错位布局。它不能继续充当修复证据。
- 曾准备 DDR 1.12 系统引导对照工件，但并未写入，也没有完成这项实验。不能把恢复启动归功于“换 DDR 固件”。
- 所有指示灯不亮不是电源或板卡损坏的充分证明；串口执行日志和可读存储证明当时仍有代码运行。本次没有完成板级电源故障的确证诊断。

**最终方案。** 使用已核实映射和读取范围的 RAM Loader，通过 Windows Rockchip 驱动发送物理 LBA 读写命令。比较源镜像与介质，跳过相同块，仅重写不同块，每块立即回读；全部完成后再从物理 LBA 0 连续读取完整 12 GiB。错误即停止，未把自动重试或复位混进写入流程。

**验证。** 完整物理回读 SHA-256 为 `73e45bf0ffe7d6fb080f475495d772dc921507eb82a791da36045d1564c1f075`，与当时发布镜像一致；正文差分改写 1,578,500,096 字节，另先行修正前 16 MiB。后续冷启动日志确实执行 U-Boot 2024.01 和新 Linux。这两个验收是分开取得的，完整回读成功本身仍不等于能启动。

**经验。** 必须证明“谁在提供读写服务”和“它的 LBA 对应哪里”。独立读取路径、有效 GPT 在不同物理偏移的位置、IDB/U-Boot 指纹和串口版本，组合起来才能排除自洽但错误的读写路径。“烧录程序太旧”过于笼统，真正已证实的是 Loader 映射不兼容。

证据：`outputs/Firefly-RK3288-TV/启动故障记录/地址偏移独立核验.json`；`地址偏移修复步骤.md`；`最终物理写入校验.json`；`UART-20261105-043213.txt`；`DDR112-对照测试步骤.md`；`work/record_address_offset.py`。

### 4. 连续 `0xCC`、32 MiB 读取边界和 Maskrom 标签

**现象。** 首次 GUI 校验在已检查约 17 MiB 的分段位置失败，导出的比较缓冲区全为 `0xCC`；加载 RAM Boot 后界面仍可能显示 MASKROM。另有一次初始 DDR USB 传输报错。

**确证原因。** 官方 v2.63 RAM usbplug 的读取限额为 32 MiB。该分段从物理 16 MiB 起写入，校验推进到其后约 17 MiB 时跨过物理 32 MiB，因而错误出现位置与限额一致。全 `0xCC` 不是已证明的 eMMC 实际内容，更不是坏块结论。

RAM 读取修正版仅改 usbplug 初始化中的一条 Thumb 移位指令，共两个字节，使读取限额扩大到 16 GiB；重新计算包 CRC，DDR、写入代码、FlashBoot 与包结构没有改变。主机仍受已识别的真实容量和每次传输长度约束，扩大软件限额不是授权越界读写。

**排查与错误路线。** 只看“下载成功”或 MASKROM/LOADER 标签不能确认 RAM 代码身份；一次主机/驱动初始传输失败也不能证明 DDR 硬件坏。改为直接检查 RAM 指令指纹、eMMC 指针、软件读取上限和跨 32 MiB 的真实数据。

**验证。** 修正版在本板通过实际 RAM 代码、容量和跨界采样验证；后续还完成整个 12 GiB 的物理回读。跨界采样时旧错位布局仍然可见，这同时说明读取修正没有暗中修复或改写存储。

**经验。** RAM Loader 是临时恢复工具，不能写进系统分区当作正式引导。若开源相关主机代码，应保留精确包的哈希与差分审计、真实容量限制和失败即停行为；本次验证范围只是这一板卡与这一包，不能宣传为通用 Rockchip 刷机器。

证据：`outputs/Firefly-RK3288-TV/启动故障记录/诊断记录.json`；`RAM读取修正/使用说明.md`；`RAM读取修正/provenance.json`；`RAM读取修正/independent-audit.json`；`RAM读取修正/硬件只读核验.json`；`work/loader-package-audit/build_readlimit_package.py`。

### 5. 新内核黑屏：最后一条 Hantro/PMU 日志不是最终根因

**现象。** 物理镜像修正后出现过早期画面，随后黑屏。新引导已经执行，但日志停在 `hantro_driver_init`，后续定点日志又停在 VIDEO 电源域、IOMMU 附着或 `notifier_pre.after` 附近。

**已证实与尚未证实。** 日志证明这些路径已经进入，却不能证明最后打印处就是第一处故障。多核异步执行、`printk` 锁、日志条数上限、串口交织和未返回的 MMIO 都可能使可见边界落后或偏离真正阻塞点。

尤其 PMU 定点日志的一部分额度已被较早 VIO 输出消耗；源码与对应反汇编显示某个被怀疑的 N1→N2 间只做整数判断和内存读取，并不直接调用 PMU/时钟。因此撤回“已经定位为物理 VIDEO 上电动作卡死”的强结论。

**已经做过、但未解决问题的路线。**

1. `initcall_debug` 和详细串口输出：帮助定位阶段，不是修复。
2. 临时跳过 Hantro：日志继续经过若干初始化后仍停住，因而不能认定上游 Hantro 本身是根因。
3. 取消 HDMI 文本控制台、减少逐函数日志、`loglevel=0`：均未使 Android 恢复，且不能独自排除全部日志锁问题。
4. 按实测 MIDR 对应的 Cortex-A12 分支启用四项上游 CPU 勘误配置：嵌入配置和汇编检查通过，但实板仍停滞，不能把这组补齐当作本次故障的已证实修复。
5. 单核试验工件曾准备，但从未写入或执行；不能写成“单核也失败”。
6. 延迟心跳、IPI 和 RAM 标记：一次观察只见 `ABD ARMED`，没有后续 dump。这不足以证明四核全部停止，因为采集器本身还依赖定时器、IRQ 和 UART。
7. 保持供电后读取残留 RAM：指纹不匹配、全零/全 `0xFF` 和非法 per-CPU 偏移令现场无效。未继续追逐这些指针，也不把它解释成有效栈或错误寄存器。

**更有效的定位。** 在独立构建中加入不依赖常规 printk 的有界直接 UART 标记，同时覆盖 Hantro、VIDEO、定制 HEVC、其 IOMMU 和运行时电源管理。这样才能看见 Hantro 注册期间另一路 HEVC 自动挂起的并发行为。直接串口仍会改变时序，字节可能交织，必须保留该观察限制。

**经验。** 我应该在每次候选试验前写明“它能区分什么假设”“什么结果会否定它”。将几项已有充分证据的配套修改一起制作和离线验证后再重启，比每次只加一个参数、再手动进入下载模式更高效。无效的排查路线和过早下的结论，也需要在复盘中明确撤回。

证据：`outputs/Firefly-RK3288-TV/启动故障记录/串口定位与当前状态.md`；`HantroProbeKernel隔离补丁/coldboot-observation.json`；`PMUProbeKernel隔离补丁/coldboot-observation.json`；`ActiveBootDiagKernel隔离补丁/coldboot-decoded.json`；`ActiveBootDiagKernel隔离补丁/retained-ram-20261107/capture.json`；`SilentSerialDiag隔离补丁/coldboot-observation.json`；`work/kernel-ca12-errata/build-validation.json`；`work/kernel-ca12-errata/independent-coldboot-observation.json`。

### 6. 定制 HEVC 路径：找到了源码缺陷，但最终采用的是隔离

**现象。** 直接 UART 追踪中，HEVC probe 完成，随后 core 的 100 ms 自动挂起关闭时钟；IOMMU supplier suspend 进入 `rk_iommu_enable_stall()` 前后边界后未见返回。同时另一个 CPU 的 VIDEO 上电路径也没有继续。

**修正过的判断。** 最初静态分析认为“probe 没直接调用 runtime resume，核心复位应该不会执行”，这不完整。media 子设备注册经过设备核心，会为父 HEVC 设备取得 runtime PM 引用。实板 T0–T8 标记确证，probe 期间确实发生了 runtime resume。

**确证的源码缺陷。** 定制 `rkvdec_runtime_resume()` 使能时钟、复位 HEVC，再调用预期的 IOMMU 恢复函数；但 `empty_domain` 在 media 注册之后才分配。因此第一次 resume 时恢复辅助函数因 `empty_domain == NULL` 而成为空操作。进入和返回该辅助函数的日志不能证明 MMU 状态已经恢复。这个初始化顺序缺陷可以从实际编译源码和调用链确认。

**尚未确证的因果。** 该复位究竟清除了哪些寄存器、如何导致本板 stall、是否同时涉及总线 idle/时钟时序，没有完成硬件级证实。不能将“存在源码缺陷”直接升级为“唯一根因已经修好”。

**失败的候选。** 参考 vendor 4.4 的时钟与关闭顺序，曾让 HEVC MMU 同时持有 ACLK/HCLK/CORE/CABAC 四路时钟，并改 IOMMU 驱动获取 DT 中全部时钟。候选写后全 boot 回读通过，实际运行仍停在同一 S1 边界。它否定的是“四时钟补齐足以恢复本次启动”，并不证明时钟毫无关系。`rockchip,disable-mmu-reset` 也不能替代 decoder 自己的 reset-on-resume 修复。

**最终恢复方案。** 只在 DT 中将定制 HEVC decoder 与其 IOMMU 两个节点设为 disabled，保持 Hantro、现有内核及其他配置不变，以恢复可启动基线。该变更的 boot 文件经过离线结构审计和完整分区回读。

**验证。** 此后 Linux 初始化继续完成，四核心跳都有响应，Android 串口 shell 出现。随后暴露的 BPF 重启是下一层问题。这是 HEVC-disabled 基线成功，而不是 HEVC 硬解成功；H.264 所用 Hantro 保留，HEVC 仍是公开版本应标注的未完成能力。

**经验。** 恢复可测试基线与修复复杂硬件单元应分开。后续 HEVC 工作须先建立正确的 supplier/master、reset、empty-domain 生命周期和失败清理，再做独立硬件验证；不要把当时的四时钟、诊断打印或半成品 reset 路线标成完成补丁。

证据：`work/original-tvbox-divergence/hevc-init-side-effects-audit.md`；`work/original-tvbox-divergence/hevc-reset-order-defect.md`；`outputs/Firefly-RK3288-TV/启动故障记录/HevcClockFix联合补丁/clockfix-uart.txt`；`HevcDisabledRecovery隔离补丁/manifest.json`；`HevcDisabledRecovery隔离补丁/independent-package-audit.json`；`HevcDisabledRecovery隔离补丁/softwareboot-uart.txt`。

### 7. 闪烁光标后重启：Android BPF 的 ARM32 门槛

**现象。** 停用定制 HEVC 后出现左上角光标，约数十秒后重启。日志明确记录 `reboot: Restarting system with command 'bpfloader-failed'`。NetBpfLoad 报告当前 Android 版本不支持这种 32 位内核组合。

**确证原因。** 有两类不同问题：Android 用户态包含平台支持门槛，实际 ARM32 BPF JIT 又不支持部分原子指令和伪函数调用。已编译的标准网络 BPF 对象包含原子操作；新 `@funcs` 对象还涉及解释器不支持的回调路径。只伪造设备类型、删掉报错或强置完成属性，会掩盖真实程序未加载，不能作为修复。

**最终方案。**

- 内核保留 BPF/JIT 能力，将 `CONFIG_BPF_JIT_ALWAYS_ON` 和自然派生的 `CONFIG_BPF_JIT_DEFAULT_ON` 从 y 改为 n，使真实解释器回退存在。
- NetBpfLoad 的例外严格限定 ARM32、当前板型与 userdebug；保留实际 load/verifier/map/program-info 检查，以及失败重启行为。
- 对确实已加载的解释执行程序允许 `jitLen == 0`，不伪造成功；在这一限定范围选择现成的 inline BPF 对象，避开不支持的 `@funcs` 变体。
- 单独重建、签名和核验 Tethering APEX/CAPEX。提取的 60 项内容中只有 `bin/netbpfload` 改变，保留原有身份，源构建工件不直接覆盖。

**验证。** CAPEX 目标区域完整回读一致，配套 boot 完整 256 MiB 回读一致；实际启动后 `bpf.progs_loaded=1`、bpfloader 正常退出。我保持开发板运行，观察时间超过此前的重启窗口，没有再出现周期性重启。这里证明的是本次 userdebug 移植可运行，不表示成为 Android 官方支持或合规的 ARM32 平台。

**错误路线和经验。** 不要把终端上已出现 shell 当作 Android 框架已经完成启动；不要把“ABI 可以编译”当作新 Android 网络栈支持这一架构。平台门槛、JIT 指令支持和对象变体需要配套检查，兼容例外必须窄化且保留真实失败路径。

证据：`outputs/Firefly-RK3288-TV/启动故障记录/BpfLoader诊断/UART-20261107-035143.txt`；`UART-20261107-040016.txt`；`work/arm32-bpf-audit/compiled-object-instructions.json`；`work/kernel-arm32-bpf-compat/config-change.json`；`work/netbpfload-arm32-compat/NetBpfLoad.patch`；`build-result.json`；`package-validation.json`；`work/CURRENT-BPF-RECOVERY.md`。

### 8. 整板不再重启，框架仍起不来：u32、memfd、AF_KEY

**现象。** BPF 通过后仍只有光标，`sys.boot_completed` 尚未出现；netd 或 system_server 反复失败。此时是服务链重启，不应继续称为“整板又重启”。

**按证据逐项推进。**

| 后续错误 | 已查清的机制 | 采用方案及验证 |
| --- | --- | --- |
| StrictController 的 IPv4/IPv6 规则找不到 `u32` revision 0 | 缺 `CONFIG_NETFILTER_XT_MATCH_U32`；netd 的 init 规则在其重启时重启 zygote | 先用与当前内核 vermagic/MODVERSIONS 匹配的模块验证，再内建；netd 继续运行，未额外改已有 connmark/state 等选项 |
| `ApplicationSharedMemory.nativeCreate` / ashmem `ENOENT` | 内核有 memfd，但默认用户态选择依赖的 SELinux memfd capability 不满足，仍尝试不存在的 ashmem；选择按进程缓存 | 在 vendor `early-init`、服务读取前设 `sys.use_memfd=true`，实际使用已有 memfd 能力 |
| `synchronizeKernelRCU failed: -97` | 本版本 Android 通过创建再关闭 `AF_KEY/PF_KEY_V2` socket 等待 RCU；内核缺 `NET_KEY`，已有 XFRM 依赖不是缺口 | 先验证兼容模块，再将 `CONFIG_NET_KEY=y`；保留真实 RCU 等待和 BPF 检查，不跳过报错 |
| 缺 `dummy0` | netd 有相应设备需求，原内核未内建 DUMMY；该警告本身记录为非致命 | 持久候选加入 `CONFIG_DUMMY=y`，不将其夸大成单独启动根因 |

**最终持久方案。** 配套内核相对 BPF-compatible 基线只增加 U32、NET_KEY、DUMMY 三项；memfd 在早期 init 中持久设置。临时模块和 live property 只用于隔离验证，重启会失效，不能作为最终镜像交付状态。

**验证。** 持久更新后新一次启动没有依赖临时模块或文件 bind 修复，模块列表为空，`sys.boot_completed=1`、`sys.use_memfd=true`、`bpf.progs_loaded=1`，system_server 与 TV launcher 正常运行；boot 和 vendor 全分区实板回读匹配候选。

**与图形/音频启动的边界。** 同阶段还发现 gralloc 分配服务意外持有 DRM master，composer 不能驱动物理显示，以及初期 HDMI 音频 policy 转为 AIDL 时 abort。前者通过释放分配器多余 master 恢复 compositor 控制显示；移除冲突音频声明当时只是止崩溃诊断，不代表声音已经恢复。后来的 ES8323 耳机修复应另作音频章节，不能将早期空输出 policy 当成最终音频方案。

**经验。** 每次只沿实际错误继续到下一层；让服务停止崩溃只是中间验收。稳定桌面、网络可达、真实音频和视频输出仍要分别测试。完整保留当时的“候选未安装”和后来的“新启动通过”记录，避免从一份离线 manifest 推断硬件成功。

证据：`work/netfilter-live-fix/README.md`；`android-net-builtin/manifest.json`；`work/runtime-boot-fixes/hardware-persistent-verification.txt`；`work/CURRENT-BPF-RECOVERY.md`；`outputs/Firefly-RK3288-TV/启动故障记录/Vendor持久修复/README.md`；`Vendor持久修复/vendor-validation.json`；`BpfLoader诊断/adb-crash-0426.txt`。

### 9. 以太网和 USB 输入：保留已经被否定或未验收的边界

**以太网现象。** 网口灯亮/闪，Linux 却显示 `eth0 UP/NO-CARRIER`、`carrier=0`，没有 IP。日志在 MDIO 的两个地址都发现 RTL8211E，因此曾怀疑自动选择了广播别名或错误地址。

**结论。** 这只是合理假设，未被证实。后续持久更新的新启动自动建立链路并取得 DHCP 地址，网关和外部连通性通过；**没有改 PHY 的设备树**。现有记录不能把链路恢复归因于 PHY 地址补丁，也不能证明最初是网线、供电、插接还是启动时序中的哪一个因素。保留初始故障与后来恢复两个事实即可。

**经验。** 灯亮、carrier、IP、默认路由、DNS、外网可达是不同层级。`NO-CARRIER` 时尚未到 DHCP，不宜直接修改 IP 或 DNS；多地址枚举也不等于已经确认地址错误。

**USB/鼠标现象。** 我遇到过鼠标不可用、重启后又恢复的情况。后续实际输入检查得到接收器的 `REL_X/REL_Y`，Android `dumpsys input` 有指向目标显示的 `HOVER_MOVE` 和启用的光标控制器。

**结论。** 鼠标在当次启动可用已经证实；热插拔是否在所有端口、接收器和启动阶段都可靠，没有专门回归证据。没有找到一个可以标注为最终“USB 热插拔修复”的明确补丁，不能把“重启后好了”解释为必须重启才能识别。

**经验。** 固定 USB-A host 与 OTG 的不同角色；依次确认 USB 枚举、evdev 事件、Android InputReader/路由和实际光标。以后补做拔插矩阵时，要记录是否整板重启、是否只是 Android 服务重启，以及输入节点是否确实重新出现。

证据：`outputs/Firefly-RK3288-TV/启动故障记录/BpfLoader诊断/ethernet-current.txt`；`ethernet-dmesg.txt`；`input-mouse.txt`；`work/netfilter-live-fix/mii-readonly-manifest.json`；`work/CURRENT-BPF-RECOVERY.md`。

### 10. 从反复手动恢复到可审计的持久更新

**问题。** 早期几乎每次试验，我都得手动断电、按 Recovery、加载 RAM Boot，反复操作花了很多时间。排查进度里又曾混用“工件已完成”“写入成功”“重启成功”，让我难以判断修复究竟推进到了哪一步。

**改进。**

- 准备完整候选后再进入一次下载状态；修改小配置时只触及已核验的扇区，修改内核/DTB 时维护 FAT 链、目录长度及 FSInfo。
- 写入器固定目标、容量、源/目标哈希和预期旧内容，逐块写验，并以完整 boot 分区回读收尾。目录长度等提交元数据放到相应数据写验之后。
- 核查标准 RockUSB 正常复位的 opcode/subcode，成功 CSW 之后才单独请求重启；正常复位与请求 Maskrom 的子命令不同，USB bus reset 也不是 SoC 正常启动的替代。
- Android 可用后审计已安装 U-Boot 的 Fastboot 实现、目标 GPT 和 128 MiB 下载缓冲区。用低于缓冲区的 sparse 分段传输完整 boot/vendor，检查每段 OKAY，再实际读取完整分区验证。此处 boot 是 FAT 文件系统镜像，不能套用普通 Android `fastboot boot` 的假设。
- 使用现有 Windows 传输路径完成持久更新，避免在没有证据时更换驱动。有一次更新前开发板返回 Android，实际是我手动重启造成的，因此没有将它记成新的自动复位故障。
- 发行镜像由固定原始镜像加审计后的分区组装，保留原始空 userdata，不把当前设备账号、调试授权或临时运行状态打包进去。

**验证。** 早期恢复完成过完整 12 GiB 物理读回；后续持久修复完成 boot/vendor 全分区读回和新一次启动验证；最终播放改进镜像还完成与其固定基线的整盘字节比较，仅允许 boot/vendor 改变。新镜像未做清空数据后的整盘重刷，这是应保留的发布限制。

**经验。** 我应该更早接入串口，取得独立证据；建立可追溯基线、最小补丁、回退工件、分层验收和自动软件复位，也能减少自己反复进行断电、按键和下载的操作。软件复位提高迭代效率，但不能替代最终完整冷启动与持续运行验收。

### 11. 对外复盘与开源材料的最小真实性要求

1. 将已实测修复、诊断补丁、准备但未执行的实验分目录；不要把 SingleCPU、DDR 对照、各轮 tracing 或失败的四时钟候选都塞进“最终修复”列表。
2. 给最终内核、DTB、CAPEX、vendor 和整盘镜像各自保留来源、哈希及验收层级。版本字符串相同，不意味着二进制相同；原始压缩镜像时间戳不变，也不意味着板上分区没有改过。
3. 已推翻的结论应明确记录：同路径回读不证明物理映射、最后日志不证明硬件卡点、probe 可经子设备注册隐式 resume、PHY 错地址未证实。
4. 本项目当前可启动且 Hantro 保留，定制 HEVC 禁用；ARM32 新 Android 支持采用的是明确限定的 userdebug 兼容路径，不能宣传成厂商认证固件。
5. 公开版只留可复用源修改、构建/验证流程和脱敏摘要。原始串口/ADB/Rockusb 日志、设备绑定脚本、签名私钥、授权信息和个人网络参数应逐项审查，不因放在 audit 目录就自动适合发布。

本复盘不替代后续显示、H.264 像素正确性、音频和实际 YouTube 性能章节；特别是“Android 能稳定进入桌面”不是“所有 4K/8K 视频可以流畅硬解”的证据。

### 1. UI、Esc 与家长页面

#### 问题及原因

### 3. 初始 AIDL 音频策略错误

#### 为什么服务会失败

原配置把真实的外接 HDMI 输出同时列为 attached/default。当前 AIDL 转换器要求 attached 设备的 connection 为空，外接 HDMI 的 connection 则是 `hdmi`；框架的 AudioPolicyConfig 和 AIDL DEFAULT_DEVICE 语义还有独立约束。仅放宽某一处断言不能使整条链路正确。

原 `ModuleFirefly` 又没有实现连接外部设备的 `populateConnectedDevicePort`，默认模块会拒绝外部端口连接。因此临时 XML 去掉 attached/default 后，HAL 不再 abort，但仍无 primary/default output。服务 running 与耳机或 HDMI 出声是不同结果。

#### 处理过程与最终范围

临时 XML 只用于让服务稳定并继续系统诊断，不伪造 Speaker，不把丢弃数据当播放。当时已经检查过 HDMI 完整实现所需的改动，但还没有完成热插拔。我随后决定先通过 3.5 mm 接口听声音，因此这一阶段先实现固定的板载模拟 DAC 总线：`AUDIO_DEVICE_OUT_BUS`，地址 `firefly-es8323`，空 connection，真实 attached/default。

该建模对应板载固定 DAC，符合接口约束；它不是把 HDMI 标签改成别的名字绕过校验。音频策略只暴露 48 kHz、PCM16、双声道输出，Android 混音器负责实际重采样和软件音量。

证据：`work/audio-aidl-audit/diagnostic/README.md`、`work/audio-aidl-audit/diagnostic/audio-policy.patch`、`work/audio-aidl-audit/HDMI-POLICY-OPTIONS.md`、`work/audio-analog-fix/audio_policy_configuration.xml`。

### 4. 板载 ES8323：路由、GPIO 与电源依次修通

#### 4.1 先建立真实的板级音频通路

原版 Firefly-RK3288 与 Reload/Plus 的硬件描述不能混用。两份独立维护的原厂时代板级源码都指向 I2C2、地址 0x10 的 ES8323，GPIO0_B2 放大器使能以及 LOUT2/ROUT2 输出。旧驱动 widget 名称与当前主线驱动不同，不能照抄旧字符串。

内核仅补入 ES8323 与 simple amplifier 驱动；DT 使用 simple-audio-card，实际模拟 PCM0、HDMI PCM1，共享 RK3288 I2S。模拟链路 MCLK 比率 256，在 48 kHz 时为 12.288 MHz，位于 ES8323 支持表。HAL 根据 ALSA 卡 ID `FireflyES8323` 寻找声卡，不假定始终 card0，也不在找不到时改投 USB/其他声卡。

最终混音器初始化严格使用实际名称：PCM 音量 192（0 dB）、输出 2 音量 21（−13.5 dB）、输出 1 关闭，左右 DAC 播放开关开启、旁路关闭、耳机 DAPM 路由开启。缺控制或写 PCM 失败就报告错误。

#### 4.2 已证实的 GPIO0_B2 冲突

实机声卡延迟注册：TSADC 已占用 GPIO0_B2，放大器申请失败；ES8323 本身已经绑定成功。板级 DT 原来就设置内部 CRU 热关断模式 0，却从 SoC DT 继承了外部 shutdown 引脚的 init/default/sleep pinctrl，恰好也是 GPIO0_B2。

修复只在 TSADC 节点删除 `pinctrl-names`、`pinctrl-0`、`pinctrl-1`、`pinctrl-2`。保持 TSADC 启用、内部 CRU shutdown、极性、95°C 硬件阈值以及 CPU/GPU 热区。驱动源码确认模式 0 选择 CRU 而非 GPIO；binding 允许此模式不带 pinctrl。不能将此项描述为“关闭温控”。没有诱发过温测试，热保护结论范围是配置和精确源码语义保留。

#### 4.3 已证实的模拟供电关闭

修复引脚后，实际 sysfs 仍显示 `vcca_18`、`vcca_33` 关闭；旧原版板 DT 的 REG7/REG8 均要求 always-on。第三版 DT 只恢复这两个属性，语义比较确认其他节点属性不变。实际 boot 写入完整回读后正常启动，两路电源启用、电压值不变，ES8323 寄存器可读，先前 I2C -110 超时消失。

#### 4.4 物理听音验收与限制

AudioTrack 播放 48 kHz、16-bit、双声道、−26 dBFS 的 440 Hz 测试，先左 2 秒、后右 2 秒，共 192000 帧。除了软件帧计数通过，我还实际听到了左右声道的测试音，这才完成模拟路由的物理验收。

该次有启动 underrun，停止后还有 `snd_soc_dai_set_sysclk(-22)`；后者可能与时钟 teardown 有关，但没有证明清零时钟就是其唯一根因，因此不称日志完全无误。耳机检测 GPIO 的插入极性未验，最终是固定模拟输出，该阶段没有自动切 HDMI（后续软件补齐见第四部分），没有建立模拟/HDMI 独立采样率同时播放能力。

### 5. “刚才有声，随后又没声”：XRUN 恢复缺陷

#### 证据链

初次听到声音后，我又遇到了播放中途失声。检查发现持续播放发生 ALSA XRUN，AIDL 流停留 ERROR。此时 AudioService 未静音、音量已达 14/15、ES8323 通信和模拟电源正常，所以继续增音量不能修复这个问题。重启旧音频服务后，我仍没有听到声音。

对旧 HAL 在真实 AudioTrack 播放时暂停 220 ms，可重现 RUNNING→XRUN，恢复执行后仍停在 XRUN。旧软件计数甚至把 4 秒样本在 2178 ms 报“完成”，证明“写入成功/计数增加”本身不足以证明声音经过硬件播放。

#### 最终修复与复验

`AudioCoreFirefly.cpp` 对零字节 AIDL burst 不调用 PCM 写；普通写失败后只关闭/重新打开同一 proxy 一次，再重试当前已经应用增益的 buffer 一次。保留累计帧计数，不重复乘增益；恢复失败仍返回错误，不把丢弃的数据报告为消费成功。

同样暂停 220 ms 后，新版实测 RUNNING→XRUN→RUNNING，不重启服务；日志记录一次写错、一次 reopen、当前 buffer 成功写回，耗时 4675 ms。随后两次 4 秒左右声道测试有真实硬件播放头，分别约 4244/4212 ms，我也再次听到了声音。仍出现过一次启动 underrun，不应夸大为零欠载。

最终 HAL SHA-256：`71d22b5fe208c269ae0f6ec56b8b9db9e80857f769a85b9669f43e56a3608935`。已在 vendor 原子持久化，保留权限/属主/SELinux 标签，移除临时覆盖并恢复 vendor 只读。该修复当时没做冷启动；后来的最终镜像整合记录明确把它列为不能更动的 guard file，后续播放验收记载声音正常。

后续 SmartTube 音频快照中，44.1 kHz 输入被正常重采样至 48 kHz，timestamp rate 为 1、discontinuities 为 0，mixer/活动 track 无 underrun。它只证明该采样窗口音频正常，不保证所有时段；也不支持继续把剩余视频卡顿归因于音频漂移。

### 6. “不支持音视频格式”与硬件解码是两个问题

此板安装的是 AIDL Codec2 服务，系统却默认选择 HIDL。AOSP 在 `media.swcodec` 启动时一次性捕获该选择：未选 AIDL 时，名为 software 的 AIDL binder 服务可以存在，但里面是空的占位 ComponentStore，list/create 返回 not supported。看到服务名，或看到 media XML 已列 AVC，都不能证明实际解码器注册成功。

修复是在服务启动前选 AIDL，然后重启精确的 `media.swcodec` 服务，并刷新消费者进程中的 codec list 缓存。仅重启名为 media 的服务不足。最初软件优先的排名属性是诊断/回退策略，不能当作最终硬件优先方案；后续硬解修复由独立记录覆盖。

自制 `CodecProbe` 真正读取 AVC/AAC/Opus 解码输出直至 EOS 并计算 CRC：720p AVC 48 帧、AAC 与 Opus 实际 PCM buffer 均通过；AVC 全部像素 CRC 还与独立 FFmpeg 软件参考一致。该工具不创建 Surface 或 AudioTrack，所以验证的是解码内容与注册通路，不是 HDMI、耳机或硬解吞吐。停用的定制 HEVC 节点也不应为了修 codec 枚举而重新启用。

证据：`work/video-codec-runtime-audit/CODEC2-AIDL-REGISTRATION.md`、`work/tv-ui-redesign/CodecProbe.java`、`work/tv-ui-redesign/codec-probe/runtime/results.json`、`work/tv-ui-redesign/codec-probe/runtime/video-reference.json`。硬件像素正确性与视频性能请交叉引用 `work/hantro-reference-timestamp-fix/FINDINGS.md` 及 `work/playback-image/hardware-evidence.accepted.json`。

### 7. 打包状态、版本判断及排查经验

最终本地整合清单包含 UI v3 的 system_ext、已修模拟音频的 boot/vendor，并保留原始空 userdata；HDMI 补齐前的播放修复整盘 SHA-256 为 `e088a501ff8b0afb2a97a6b6f397b9b4f1a5e14cfaadfec5af5a94d8f8de2d09`。`merged-payloads.json` 的 released 是本地镜像整合状态，不能据此声称已上传公开仓库或已完成法律审查。`full-image-pre-release-audit.json` 明确记录整合范围和空 userdata 保留；它不是全新清空设备重刷验收。

我曾看到最初下载的镜像时间戳一直没变，因此怀疑修复是否真的写进去了。实际情况是，板上分区在更新，而最初下载的整盘文件被保留为基线；镜像离线替换也可能保留文件 inode 时间。因此不能只靠时间戳判断版本，而应核对文件/分区散列、写入及回读记录、实际运行服务与我观察到的现象。

本次有价值的经验：

1. 服务不崩溃、接口可枚举、PCM 可写、物理出声分别验收。早期候选通过源码审阅不等于具备听音结果。
2. 先固定板型再查硬件路由。设备树中 pinctrl 和 regulator 这种看似无关配置，会让 codec 存在却没有声音。
3. 保持真实接口语义。不要把 HDMI 假报为 Speaker，也不要丢弃样本同时报告播放成功。
4. 短测通了后做可控故障恢复测试。220 ms 暂停提供了明确的前后复现，效率与证据强度都优于反复重启猜测。
5. UI 取消/返回路径应与主路径同等测试；尤其 PIN 页面不能通过删安全逻辑来解决焦点或空白页。
6. 我通过软件注入得到的结果，不能替代实际按键和插拔验证。热插拔、Fn 音量、遥控器兼容性没有验证就保留为待测。
7. 打包以最终有效来源及清单为准。早期 HAL、第一版 APK、设计稿、临时 XML 都应明确标为历史，而非混入发布文件。

### 2. 为什么“已经启用硬解”仍然会卡

本项目的链路是：播放器 → Android MediaCodec/Codec2 → FFmpeg 的码流解析与参考帧管理 → V4L2 Request → Hantro VPU → NV12 图像 → Codec2 图形缓冲区 → gralloc → SurfaceFlinger/HWC → DRM/VOP → HDMI。

VPU 负责解码，并不自动负责播放器选码、缓冲分配、像素搬运、颜色转换、合成、显示时钟和呈现调度。任一环节出错，我在屏幕上看到的都可能只是“卡顿”“黑屏”或“花屏”。因此排查时需要分别回答：是否调用硬件、像素是否正确、交付能否达到实时、显示是否及时、真实播放器是否稳定，而不能用一个“硬解成功”包办。

最终 NV12 路径减少了不必要的中间复制与格式转换，但仍将图像复制到 Codec2 graphic block；它不是端到端零拷贝。最终 CLIENT 合成仍由 GPU 完成，也不等于所有视频都走 VOP overlay。

### 3. 从闪烁光标到 Android：DRM master 被错误持有

#### 问题与原因

HDMI 已连接，但 SurfaceFlinger 只建立没有 EDID 的 headless 显示，屏幕保留 fbcon 的闪烁光标。运行状态显示 gralloc allocator 持有 `/dev/dri/card0` 的 DRM master，而 composer 没有 master。

minigbm 的 Android `cros_gralloc_driver::init_try_node()` 打开 primary DRM 节点后，保留了自动获得的 master。分配缓冲区并不需要占有显示控制权；同库的另一条辅助路径已经会释放这种意外获得的 master，Android 路径却没有。

#### 过程与修正

一次性让 allocator 放弃 master 后，再重启 composer，另一个 gralloc 使用者又可能先取得 master。因此只释放某个进程的当前 FD 不是持久修复。最终在成功 `drv_create()` 后，对 primary 节点检查 `drmIsMaster()` 并调用 `drmDropMaster()`；失败则清理资源并返回错误。该修正进入共享 gralloc 库，覆盖所有相关使用者。

#### 验证与经验

应检查 composer 的实际 master 身份、真实 HDMI/EDID、scanout 从 fbcon 转为 Android，以及启动完成状态。库编译成功或某次释放成功不等于图形栈完成修复。

证据：`work/graphics-runtime-audit/DRM-MASTER-DIAGNOSIS.md`、`work/graphics-runtime-audit/cros_gralloc_driver.patch`；最终 gralloc 还叠加了下一节的 NV12 修正。

### 4. NV12 分配失败：把“可作纹理”误当成“必须直出扫描”

#### 问题与原因

硬解产生 NV12，但播放器反复分配失败、重建解码器。Surface 的 usage `0x400933` 含 `HW_COMPOSER`，minigbm 将其转换为 `BO_USE_SCANOUT | BO_USE_TEXTURE`。generic rockchip 后端支持作为纹理的视频解码 NV12 缓冲区，却没有声明支持相同组合的 NV12 scanout。旧 resolver 在分配前就拒绝了它。YV12 原有专门 fallback，因此其表现不同。

#### 修正

只在以下条件同时满足时重试：驱动为 rockchip、格式为 NV12、用途包含视频解码和纹理及 scanout、原组合不支持、去掉 scanout 后的组合支持。只去除 `BO_USE_SCANOUT`，不虚假声明新的 scanout 能力，也不改变其他格式/驱动的一般分配规则。

#### 验证

独立 allocator probe 使用相同描述符：1920×1080、格式 35、usage `0x400933`。旧库返回 unsupported / allocate `-22`；候选返回 supported / allocate `0`。去除 compositor 使用位的纹理对照 `0x400133`，新旧库都成功。候选分配为 NV12 两平面，stride 均 1920，offset 分别为 0 和 2073600。ABI、动态依赖、导出符号和内存保护属性单独核验。

这只证明分配成功，像素正确性和帧率需另外验证。allocator 长驻进程加载共享库，仅重启 Codec2 不会应用 gralloc 更新；服务依赖又可能连带重启 SurfaceFlinger，实验时必须明确影响范围。

证据：`work/nv12-gralloc-fix/README.md`、`cros_gralloc_driver.patch`、`allocator-probe-results.json`、`abi-audit.json`。

### 5. 降低搬运与转换成本，但不把它冒充根因

`ffmpeg_hwaccel.cpp` 改为只读映射硬件 NV12 图像，保留硬件帧引用和同步生命周期，避免先复制到一张临时完整图像，再做最终拷贝。`C2FFMPEGVideoDecodeComponent.cpp` 为匹配的 NV12 源和目标实现按 plane/stride 的直接复制路径，非匹配布局保留原格式转换，并检查转换输出行数。

发布 Codec2 buffer 之前，先让写映射离开作用域，确保解锁及 cache 同步已经完成。该顺序修正是合理的并发防御措施；没有证据证明它就是下面像素损坏的根因。

早期 ByteBuffer CRC 不一致还需要排除测试方法错误。`color-format=19` 请求的是 I420；平台可能把 NV12 graphic block 转成 I420 返回，不能直接拿其 bytes 与 NV12 参考哈希比较。检查实际 plane、row stride、pixel stride 后仍有错误，最终下沉到独立原生 VPU 测试复现。某次 CRC 测试同时存在播放器重试循环，也不宜作为干净性能数据。

证据：`work/nv12-codec-fix/ffmpeg_hwaccel.cpp`、`C2FFMPEGVideoDecodeComponent.cpp`、`work/playback-clock-audit/NV12-BYTEBUFFER-AUDIT.md`。

### 6. H.264 像素损坏的真实原因：合法 DMA 地址 0 被当成缺失引用

#### 如何确认不是布局误读

原始 vendor FFmpeg 库和原始独立解码器，不经 Codec2 也能复现同样的错误。60 帧 1080p30 样本的期望 NV12 SHA-256 以 `397785a7` 开头，错误结果以 `71be2cf1` 开头。第 5 帧的 3,110,400 个可见 YUV 样本中有 224,975 个不同，PSNR 约 28.97 dB；第 7 帧完全相同。图像中的移动对象位置错乱，符合参考帧重建问题，不能用“允许的舍入误差”解释。

#### 用对照实验缩小范围

| 实验 | 结果 | 实际意义 |
| --- | --- | --- |
| 每张图使用唯一 V4L2 时间戳 | 错误哈希不变 | 不支持时间戳碰撞是本例根因 |
| AVFrame 内的 CAPTURE 句柄存 index+1 | 错误哈希不变 | 不支持用户态把下标 0 当空句柄是本例根因 |
| `extra_hw_frames=1` | 换成另一错误哈希 | 分配位置影响现象 |
| `extra_hw_frames=2/4/8` | 像素哈希正确 | 只是定位线索，不能直接当最终修复 |
| 恢复默认池 | 原错误恢复 | 证明不是测试偶然通过 |

额外缓冲区让实际使用的 CAPTURE 下标避开 0；默认分配会使用 0。第一张出错 B 帧正好引用下标 0 的正确 P 帧。进一步检查 ARM32 legacy DMA IOMMU 分配器，发现其地址池可以分配合法 IOVA 0；而 `hantro_get_ref()` 用 0 表示“找不到参考”，调用者也把 0 替换成当前输出缓冲区。

#### 最终修正与边界

将“缺失引用”的哨兵改为同类型的 `DMA_MAPPING_ERROR`，覆盖 5 个调用文件内的 11 个 `hantro_get_ref` 调用，包括 H.264、MPEG-2、VP8。所有缺失检查都先于 H.264 field/POC 标志或 VP8 sign-bias 位的合并，保留合法地址 0。

独立审查又发现后处理分配失败也会返回地址 0，但对应 CPU 指针为空。v2 增加这个错误边界检查，避免把真正分配失败误当成合法 DMA 0。最终没有保留额外 CAPTURE 预分配 workaround。

#### 硬件验证

修正内核运行后，定点日志明确记录“找到的 CAPTURE 参考，其 DMA=0 被保留”。默认缓冲池、原始 vendor FFmpeg 和原始独立解码器下，720p 与 1080p30 短样本哈希正确；12 秒 1080p60 共 720 帧的 NV12 SHA-256 也与软件参考完全一致。

720 帧哈希测试耗时约 39.20 秒，包括 CPU 图像传输和逐像素哈希；这是正确性测试，不是“解码只能 18 FPS”的性能测量。最终内核 SHA-256 为 `8c044786118434fc737d9c17b32bdbe4206fcd4112b625d30f29a4ba3124317a`。

证据：`work/hantro-reference-timestamp-fix/FINDINGS.md`、`pixel-comparison.json`、`fixed-kernel-short-results.json`、`fixed-kernel-long-results.json`、`fixed-kernel-dmesg.txt`、`kernel-dma-zero-v2/dma-zero-reference.patch`、`work/surface-performance-benchmark/dma-zero-independent-review.md`。

### 7. “60 Hz”模式实际只有 55.56 Hz：显示时钟必须实测

Android 公布原生模式为 1600×900@60，模式期望像素时钟 108 MHz，总周期 1800×1000。但 active VOP 时钟来自 400 MHz CPLL，实际只能得到 100 MHz；内核 vblank 连续间隔约 18 ms，物理刷新率为 `100000000 / (1800×1000) = 55.5556 Hz`。

内核会把请求时钟舍入到可实现的值用于 adjusted mode，而用户态仍看到原模式。这里没有有效的时钟精度拒绝逻辑。只看显示菜单或 `activeMode=60` 会漏掉该问题。

临时 1080p60 模式使用 148.5 MHz，已有 594 MHz GPLL 能整除，vblank 恢复约 16.667 ms，帮助隔离时钟因素。最终为了保留显示器原生分辨率，将 DTB 中 NPLL 指定为内核表中支持的 216 MHz，使 VOP 可二分得到 108 MHz。此 DTB 与前版只有一个 32 位 rate cell 不同，音频和 HEVC 节点配置保留。

NPLL 不是只属于 VOP，静态候选时检查了其他消费者；不能笼统将更改 PLL 当作无影响。最终启动后检查实际时钟/vblank，网络和播放基线仍正常。这个修正针对当前原生模式，通用驱动仍可改进为拒绝过大的像素时钟偏差。

证据：`work/nv12-gralloc-fix/DISPLAY-CLOCK-FINDINGS.md`、`drm-vblank-results.txt`、`drm-vblank-1080p.txt`、`work/display-npll216-fix/dt-audit.json`、`work/playback-image/prepare_display_dtb.py`、`work/nv12-codec-fix/postboot-vblank.txt`。

### 8. 物理 60 Hz 下仍只呈现 30 FPS：SurfaceFlinger 调度预算

#### 现象与修正

修正 NV12 路径后，解码交付约 60 FPS，但在已独立验证的物理 60 Hz 输出下，实际呈现仍经常是 33.333 ms。原 SF late/early/earlyGL 工作预算为 15,666,667 ns，应用为 16,666,667 ns。legacy framebuffer 只有两个槽，GPU backpressure 默认开启。

把 SF 工作预算统一改为 20,000,000 ns，应用预算保持 16,666,667 ns，实际间隔大多从 33.333 ms 变为 16.667 ms。源码路径说明 frame targeter 会判断先前 present fence 是否已完成，backpressure 可能跳过 commit；超过单个刷新周期的预算允许使用跨两个 vsync 的流水线。证据支持调度/流水线不匹配，但不等于每个残余漏帧都由它引起。

#### 一个重要的错误推断

曾考虑 RenderEngine 平均约 18 ms 是否说明 GPU 算力达不到 60 FPS。源码显示该计时覆盖提交、队列等待、目标缓冲 fence 等，不能解释为纯 shader 执行。20 ms 预算试验中，RenderEngine 平均时间反而从约 18.069 ms 增到 19.073 ms，而实际呈现速率接近翻倍，直接否定“这个统计值就是纯 GPU 上限”的用法。

#### 持久化时又发现初始化问题

首次持久化省略 early app 参数，认为会继承 late app 默认值。实际重启后 early/earlyGL app 为 0。对应源码的委托构造函数在目标构造函数初始化成员前就求值 `value_or(mAppDuration)`。最终明确设置 early 与 earlyGL app 两个值；late app 的字面默认值 `-1` 才能安全解析为一刷新周期。

最终在 SF 启动前设置：

```text
debug.sf.use_phase_offsets_as_durations=true
debug.sf.late.sf.duration=20000000
debug.sf.early.sf.duration=20000000
debug.sf.earlyGl.sf.duration=20000000
debug.sf.early.app.duration=16666667
debug.sf.earlyGl.app.duration=16666667
```

这些值是在 60 Hz 下验证的配置，不是任意刷新率的通用推荐。不能与旧 phase-offset 属性混用；这个源版本会拒绝相互冲突的配置。只修改属性也不会替换正在运行的 SF 配置对象。本次 runtime reload 使用已核对的 transaction 1047；1018/1019 在此版本实际上仅影响应用 EventThread，不能照旧注释理解。数字 binder transaction 属内部接口，我在记录时必须注明对应源版本，不能跨版本照搬。

证据：`work/surface-performance-benchmark/scheduling-audit.md`、`sf-scheduling-current.txt`、`budget20-steady-analysis.json`、`init.fireflyrk3288.sf20-appbudget.patch`、`work/nv12-codec-fix/final-native60-complete/surfaceflinger-playing.txt`。

### 9. 为什么没有把硬件 overlay 作为最终答案

独立 HWC 候选允许开启 overlay，并实测得到 DEVICE 视频合成，说明这条通路可用。但 KMS plane 宣布 NV12、atomic TEST_ONLY 成功，都不能证明 BT.709 矩阵及 full/limited range 正确。

查到的下游 CSC_MODE 寄存器字段限定 VOP 3.2 及以上，而原版 RK3288 是 VOP 3.1。不能凭更新版本的寄存器描述向老硬件写位；现有证据也没有证明 overlay 当前色彩一定错误，只是未验证。最终恢复原 HWC、保留 CLIENT，让 Mesa 依据 Android dataspace 做颜色转换。由于 CLIENT + 修正调度已能达到本地 60 FPS，无需把未验收颜色路径塞进已工作的基线。

证据：`work/hwc-overlay-fix/README.md`、`properties.patch`、`csc-reference-downloads.json`；该候选应作为实验补丁归档，不能混入最终默认补丁系列。

### 10. 测量工具也会误导：如何建立可信性能证据

#### MediaCodec rendered 回调并不总是“已经显示”

本平台 `CCodecBufferChannel::renderOutputBuffer()` 在 `media_native/render_metrics_enabled=false` 的默认路径，会立即将请求呈现时间作为 rendered 时间回调。一次测试回调恰为 60 FPS、lateness 为 0，但实际输出只有约 51.33 FPS、交付 lateness P95 已达 1.93 秒。这个矛盾促使回看框架源码，确认回调只是请求时间的回声。

因此 benchmark 保留历史 JSON 字段，但 README 明确禁用 `steadyRenderedCallbackFps`、回调 lateness 和回调数量作为当前固件的呈现验收。`completedWithoutError` 也仅表示 API 测试完成，不表示性能通过。

#### 单独测试像素、交付、呈现与物理刷新

1. 原生 VPU gold hash 测试验证像素；不能用包含哈希开销的耗时评价播放。
2. Surface benchmark 固定 `c2.firefly.h264.decoder`，异步供给，真实 SurfaceView，无网络、无音频，默认不主动丢帧；在首个输出后 250 ms 建立固定时钟，不能随每帧迟到不断重锚以掩盖问题。
3. 独立只读采集 `dumpsys SurfaceFlinger --latency`。按实际 BLAST layer 分组，避免把 Activity 重建前后混为一个播放。
4. 用 desired 时间戳去重重复快照和 pending 更新；完整检查 12 秒源时间格点共 720/360 个。部分 history 不足以宣称已覆盖“第 2–12 秒”。
5. 实际时间戳需要去重：多个源帧可能共享同一实际时间。`--latency` 又没有直接导出 Presented/Dropped 状态，zero-ready 只能先作为线索，再与 TimeStats 的显式 droppedFrames 互证。
6. TimeStats 的毫秒直方图会让平均 FPS 出现 62 等偏差；准确速率应用纳秒间隔计算，不能只抄其 averageFPS。
7. DRM vblank 和 clock tree 验证物理输出频率，与 compositor render rate 分开记录。
8. 最后再用实际播放器和我的观看体验验收网络、选码、音视频和 UI 干扰；本地样本达标不能替代这一步。

#### 测试自身的兼容性失败

benchmark 第一版把 extractor 的可选 AVC level 4.2 请求原样传入，当前组件只宣称 level 4.1，configure 阶段即被拒绝。1.1 改为像普通播放器一样只传必需的尺寸、帧率和原始 CSD，让 SPS 描述真实 profile/level。码流仍是 High 4.2、1080p60，没有偷偷降低样本。

它证明强制硬件路径可以处理该测试，却不自动扩大 codec XML 的公开能力上限。后续应单独整理能力声明与覆盖测试，不能通过去掉检查把“广告支持”当成已经合格。

工具与记录：`work/surface-performance-benchmark/BenchmarkActivity.java`、`README.md`、`collect_surface_latency.py`、`analyze_latency_window.py`、`final-native60-complete-independent.json`、`final-native30-independent.json`。

### 11. 排除项、剩余问题与停止条件

音频时钟曾是可能原因，但 ALSA 多次观测约 48 kframes/s，AudioFlinger 显示速率 1、输出 48000 Hz、没有对应窗口内持续 underrun；播放器 44100 Hz 音轨被正常重采样。C2 借 packet PTS 传递 frameIndex，是 work 的关联 token，输出恢复真正媒体时间戳。没有证据支持把它简单改成微秒可修好卡顿。保留已经正常的音频 HAL，避免引入新变量。

最后的真实 SmartTube 样本保存 1199 条唯一 timeline rows、640 个不同 actual event，约 22.20 秒内 28.78 event/s；期望时间持续约 16.667 ms，而实际时间经常按 33.333 ms 成对。日志出现 renderFrameRate 30/60 切换，physical mode 仍为 60。播放器本身也有 `dropOutputBuffer`，并非完全由工具统计造成。

该证据把后续优先级指向显示渲染速率选择及播放器投票，但尚未证明精确策略触发条件，也不能说每次漏帧都由它引起。视频层当时未见明确的帧率投票；临时 `min_refresh_rate=60` 试验未验收，已恢复原值 `null`，未纳入镜像。我决定先保存改善后的基线，记录小卡顿，后续再优化，而不是继续没有明确终点地调参。

后续建议使用同一视频/编码/清晰度/帧率作对照，记录播放器选择、媒体 PTS、frame-rate vote、SF render rate、实际时间戳、CPU/GPU 与音频状态；设置试验只改变一个变量，保留原值并核验恢复。

证据：`work/playback-clock-audit/FINDINGS.md`、`POSTFIX-REMAINING-STUTTER.md`、`work/surface-performance-benchmark/youtube-render-policy-pending.md`、`work/nv12-codec-fix/youtube-final/live-latency.json`、`current-logcat.txt`、`current-sf.txt`。

### 12. 应带到公开项目的工程经验

- 为每一层建立独立验收：硬件 API 存在、真实硬件帧、像素正确、实时交付、实际呈现、物理时钟、真实应用。这能避免只见“硬解 decoder 名称”就提前报喜。
- 失败假设和撤回内容要保留：额外缓冲区不是根治；回调 60 FPS 不是实呈；RenderEngine 时间不是纯 GPU 时间；overlay 成功不是颜色正确；本地 60 FPS 不是 YouTube 60 FPS。
- 新改动先做可控实验，再整合持久镜像；记录原始文件、候选、写入回读和冷启动后的有效状态。临时覆盖成功不能代替持久版本验证。
- 把可恢复动作尽量交给软件，但每次硬件操作前都先准备好下一份候选和明确要验证的假设，避免自己反复进入下载模式却没有取得新证据。
- 发布源码必须包含实际使用的补丁组合、准确基线、构建方法和测试方法。分开标注最终、实验和弃用补丁，不把整个私有诊断目录无筛选上传。

应公开的具体源码、补丁、工具及许可证范围见同目录 `benchmark-source-map.md`。

## 第四部分：随后补齐 HDMI 音频

### 1. 为什么耳机有声，HDMI 仍然无声

播放问题改善后，我又发现“HDMI 无声，3.5 mm 有声”。当时连接的仍是 DELL P2017H；读取到的 EDID 校验正确，但 CTA 的 Basic Audio 标志为假、没有 Audio Data Block，ELD 的 `sad_count=0`。这是“有 HDMI 图像”与“接收端支持 HDMI 声音”的区别，不能靠系统强制发送 PCM 给显示器增加扬声器能力。

软件也确实缺了一层。为了先让 ES8323 出声，已验收 HAL 仅接受 `OUT_BUS/firefly-es8323`、只打开板载 PCM0，音频策略只有模拟默认输出。内核虽已有同一卡的 PCM1 HDMI 接口，却不等于 Android 已有 HDMI 路由。这项遗漏不能用“显示器不支持音频”掩盖。

早期误把 HDMI 声明为 attached/default 会触发 AIDL 语义约束；补齐时没有再重复这一做法。HDMI 保持真正的外接 `OUT_DEVICE + connection=hdmi`，模拟声道保留唯一 attached/default。

### 2. 软件修正

1. 音频策略新增 `HDMI Out` 外部模板，模板地址必须为空，连接实例再使用 `firefly-hdmi`；只声明实际实现的 48 kHz、16-bit、双声道 PCM。没有声称压缩直通、多声道、ARC/eARC 或独立双路同时播放。
2. HAL 实现 `populateConnectedDevicePort`，由 AIDL Module 分配真实 connected port 并复制有效路由；根据声卡 ID `FireflyES8323` 找卡，不硬编码 card0。模拟用 PCM0，HDMI 用 PCM1，能力和 PCM 参数不符就拒绝连接。
3. Binder 线程只更新原子目标；音频工作线程负责先关闭旧 PCM、再打开新 PCM，避免两个端点争用共享 I2S。保留零字节 burst、软件音量和有界 XRUN 恢复。跨设备切换不是保证无缝的双路输出。
4. 增加平台签名的 `FireflyHdmiAudio` 系统服务，监听轮询实际 DRM 连接与 EDID，通过 `AudioService.setWiredDeviceConnectionState` 通知框架。它不伪造 attached HDMI，也没有修改所有 AOSP 产品的默认设备规则。
5. 能力判据要求当前 HDMI 已连接、EDID 头/长度/各块校验有效、CTA revision 合法，并具有 Basic Audio 保证或同一条 LPCM SAD 同时支持双声道、48 kHz、16 bit。不支持的显示器保持模拟输出；支持音频的接收端才申请 HDMI。

### 3. 这次又避免了哪些误判

某些常见 ALSA ELD 接口有 `monitor_present` 和 `eld_valid`，本内核的 `hdmi-codec` 文本并不输出这两个字段。初版解析若强制要求它们等于 1，会把正常电视也全部拒绝。修正为仅在字段存在时解释，且以当前原始 EDID 为必要依据。

进一步读内核源码发现：拔线时 raw ELD 会清除，已经解析出的 proc 文本却可能暂存；因此不能用“旧 ELD 或新 EDID 任一支持”来判定。新 EDID 明确无音频时，旧 ELD 不得将其抬回支持状态。ALSA `pcm_params_get` 在 SAD=0 时也可能给出默认 32/44.1/48 kHz 和双声道约束，不能把“PCM 能打开”当成接收端有扬声器。

Java 与 C++ 的 EDID 长度、CTA 版本和 Basic Audio 口径也做了统一。能力检测是跨进程契约；两边各写一个看似合理的判据却不一致，会形成“服务一直报告连接，HAL 一直拒绝”的循环。

换接支持 HDMI 音频的 `32V3H-H6A` 后，我确认 EDID 和 ELD 都支持双声道、48 kHz、16 bit LPCM，但 Android 仍然只有模拟输出。日志显示 monitor 不断请求 HDMI 连接，框架立即返回 `-22`，尚未调用 HAL 的能力检查。这暴露出我上一版策略的另一处缺陷：我把外部模板的地址也写成了连接实例地址 `firefly-hdmi`。`Hal2AidlMapper::setDevicePortConnectedState` 查模板前会清空地址，再按包含地址的完整设备描述匹配，因此找不到这个固定地址的模板。

修正方式是只把 HDMI 模板改成 `address=""`，保留 monitor 和 HAL 对具体实例地址 `firefly-hdmi` 的使用。框架找到空地址模板后，`Module::connectExternalDevice` 会把实例地址复制到新连接端口。模拟设备地址不变。这项缺陷不需要重编内核或 HAL；它也说明，无音频显示器上的“不误连”验证无法覆盖真实 HDMI 音频设备的成功连接过程。我随后单独完成了真实设备连接和听音验证，没有用上一版的“软件集成通过”替代它。

## 第五部分：部分直播频道跳转 Kodi（最初离线候选与后续板测）

本节前四小节保留最初准备候选时的记录。之后我已经持久安装配套组件，
完成指定音频解码器探针和部分实际直播。最新结果以第五小节及独立
[福建频道专项复盘](福建频道专项复盘.md) 为准，不能继续把历史“未安装”
状态当作当前状态。

### 1. 我遇到的现象与实际分流规则

HDMI 声音和拔插恢复通过后，我继续看电视直播，遇到了部分频道直接跳到 Kodi 的问题。界面上的表现容易让人以为只有央视留在电视应用里，但检查代码后，真正决定去向的是台源中的 `player` 提示和旧音轨选择规则。

较早的历史叠加表有 193 个频道、261 条线路，其中 239 条走内置播放器、22 条指定 Kodi。这 22 条的历史音轨标注中，18 条只有 AC-3、3 条同时有 AAC/AC-3、1 条是 MP2。旧选择器将 AAC/MP3 留给原生播放器，其余交给 Kodi；`LiveActivity` 又直接执行这个外跳选择。这解释了配置与跳转行为的关系，但我没有把旧表中的音轨标注当作本次实测解码结果，也没有把这组历史统计当作现在的线路可用率。随后核对实际打包配置，当前是 200 个频道、268 条线路；我针对这份实际清单重新检查了构建主机上的网络可用性，结果单独记录。

### 2. 先消除自动外跳，再配套补音频

我把直播统一保留在内置页面：忽略历史 `player` 提示，删除 `kodiStream` 和委派播放状态，继续通过 `MediaPlayer.setDataSource` 传入原请求头。换台、换线路、节目更新与返回仍由同一个直播页面处理。应用页主动打开 Kodi 的入口保留。

## 第七部分：我把功能入口逐项验到实际操作

我在这一轮发现，之前验证“页面能打开”仍然不够。网络页面虽然能进入，却没有有线 IP 和代理设置，也没有可工作的无线配置；分辨率页面同样能打开却没有选项。我把验证拆成入口、可编辑内容、取消与返回、实际后台状态几个层次，发现两个具体的 TvSettings 判断错误。

有线网络被错误地依赖到 Wi-Fi 服务：系统没有 WifiManager 时，通用网络监听也没有注册，以太网明明已经连接，页面却把它隐藏了。我将通用监听移出无线条件。分辨率页则在系统没有开机首选模式时直接退出，忽略了显示器实际提供的模式。我改为继续列出支持模式，保留原来的确认与恢复机制。新版 TvSettings 已装到板上，实际显示有线连接状态，可以进入静态 IP、手动代理编辑页和分辨率列表；测试没有保存新 IP、代理或改变显示模式。这些证据不等于无线已经可用。

儿童区也从简单入口扩展为算术练习、启蒙视频和学习记录。针对 3–6 岁，我提供数一数、加法、减法、比大小和混合练习，范围可选 5、10、20，每轮 5 或 10 题。答错可以重试，完成整轮才记录首次答对率；自由算术不扣视频时间，也不增加续看额度。板上五种题型各完成五题，每轮故意错一次再改正，结果均显示首次答对 4/5，返回与配置保留也通过。

家长控制需要测试真实生命周期，而不只是计时函数。我使用独立验证包建立临时 PIN，保留正式应用的 PIN、观看额度和允许列表不动。在实际设备上验证离开设置后必须重新验证，取消门禁不暴露设置，Back、Esc 和儿童页返回按钮都要求 PIN；算术不计视频时间，内置短片会计时，重复启动监控服务不会打断短片。验证包完成后已卸载。主机上的计时、PIN、恢复和并发测试与这些设备 UI 证据分别记录，跨日、真实断电和完整外部应用组合仍不能由短测推出。

其他操作也逐项检查：数字选台、无效频道号、上下换台、左右切线路、收藏切换并还原、地区与新闻/儿童分类、面板外点击和直播返回；应用管理、更多设置、重启与 USB 维护确认的取消；音量减小、恢复和静音切换。H.264 指定硬件组件完成了本地 1080p 样片的 300 帧解码。当前没有 H.265 硬解组件，因此我将对应测试按钮明确标为未启用，没有把软件预览当硬解通过。两段儿童短片实际获得连续帧进度和返回证据，原有 167 台目录与 Codec2 服务散列保持一致。

审查还发现两个直播生命周期缺陷：普通直播收到正常结束事件时没有后续处理，可能停留在末帧；旧线路的延迟重试没有播放代次约束，切台后可能再次重启新频道。我加入最多三次快速重连和明确终止提示，释放或切台时取消旧任务，并在回调中核对播放代次。我随后用独立验证包的本地短片触发真实结束回调，验证初次播放加三次重连后停止、手动换台恢复、旧重试取消和退出释放。正式节目单保持原样。

我还追到了混用鼠标和方向键时的首键丢失：Android 在退出触摸模式并重新分配焦点时，会在 Activity 收到事件之前消费第一个导航键。只在 Activity 增加按键分支并不能解决。我让播放根布局在触摸模式下保留合法焦点，选台关闭时交回播放焦点，面板内显式切换到目标控件。新版已验证鼠标进入直播、鼠标开关选台后第一下方向键立即生效，分类单击仍然正常。

网络输入向导也需要区分“退出编辑”与“离开页面”：第一下 Back 只结束文本编辑，第二下回 DHCP/静态或代理方式选择，第三下回网络页。逐次实测确认能正常退出，不能用之前强制关闭进程的操作替代取消验收。

第三方应用则必须查看新时间窗口内的日志。奇异果曾因动态插件资源引用失败崩溃；主安装包与官网完全相同，动态 EPG 插件留有崩溃回退记录。回退后我观察约 45 秒的启动和前后台切换，进程保持稳定、没有新崩溃；这不代表会员内容、长期播放或后续插件更新都已通过。

本轮详细证据和仍需实物、账号或长期测试的范围见 [儿童算术与功能验证](儿童算术与功能验证-20261108.md) 与 [网络和分辨率修复](tvsettings-repair.md)。已安装的应用、系统分区更新与旧整盘镜像仍分别标识。

## 第八部分：我把 Wi-Fi 从缺失链路推进到真实扫描

我原先看到网络设置页缺少无线选项，以为只需要补一个入口。继续往下检查后，
我发现缺的是四层配套：板级 SDIO 描述、匹配的内核模块与固件、Android 原生
无线服务，以及框架选路和产品配置。单独让页面显示一个 Wi-Fi 开关，无法让
这些缺失的链路自动出现。

我先在已有音频、显示修正的最终 DT 上追加原版板 SDIO 配置，再从匹配内核
导出 `cfg80211`、`brcmutil`、`brcmfmac` 和三个实现模块。我逐一检查 ARM32
格式、vermagic 和 517 个导入符号 CRC，避免拿同版本号但不同配置的模块来凑。
固件也按实际芯片重新确认：板上识别到 BCM4339/2；构建机的 Broadcom 文件名
背后实际是 Cypress 固件链接。我固定了下载与内容散列，保留对应许可，没有把
未确认再分发权的 AP6335 校准模板放进公开源码。

原生服务这一层让我再次碰到了“文件名存在就当成功”的陷阱。
`/system/bin/wificond` 当时只是悬空链接，真实目标和 init service 都不在镜像里。
我补齐 AOSP AIDL supplicant、实际 `system_ext/bin/wificond`、运行依赖和 RC，
同时检查了运行链接命名空间，避免误把编译用 LLNDK stub 当成运行库。

补齐 daemon 后，框架仍没有自动走到它。我沿当前源码追到 `WifiInjector` 和
`Nl80211Native`：这版 AOSP 默认开启从 wificond 迁移到直接 NL80211 的路径，
而且在构造时确定选择。init 中没有 wificond service 时，还会强制选择新路径。
因此，事后只启动 wificond 并不够。我加入只覆盖一个布尔资源的静态 RRO，
把 `config_wificondMigrationEnabled` 设为 false，并让真实 RC 和 RRO 一起在
SystemServer 启动前生效。软件重启后，我实际读回 false 和两个 Binder 服务，
再要求 Android 框架发起扫描，没有把进程存活当作无线已经可用。

板级仍有一个没有彻底解决的问题：初次 SDIO 枚举报 `-84`。我验证了受限的
控制器重新绑定可以恢复，再把它做成启动时最多执行一次的措施。脚本严格核对
内部 `ff0d0000.mmc`、host 与启动分区映射；遇到未知卡、部分枚举或再次失败
就停止，不触碰 eMMC，也不无限重试。这解决了本次软件重启后的可用性，但我
还没有证明底层电源、复位或总线时序的根因，不能把绕过措施写成硬件时序修复。

第二次软件重启不需要我手动重新绑定：SDIO 在约 18.08 秒出现，固件在
19.95 秒就绪，Android 实际扫描到 8 个热点，其中 6 个在 2.4 GHz、2 个在
5 GHz。有线链路保持连接，最终 system_ext 和 vendor 仍为只读。我没有输入
无线密码或连接热点，所以关联、DHCP、无线联网、掉线恢复和冷断电首启都保留
待验。热点名称、BSSID、MAC 和原始网络日志没有进入公开记录。

这次的经验是先证明 SDIO 枚举，再证明固件与接口、原生服务、框架扫描，最后
才做认证和联网。每层都需要自己的证据，不能用设置页、文件链接、服务存活或
一次扫描替代下一层。构建方法与限制见 [Wi-Fi 接入记录](wifi-bringup.md)，
脱敏计数与内容散列见 [验证 JSON](validation/wifi-bringup-20261108.json)。

## 最后：这次应保留下来的工程方法

### 为什么过程拖长了

最初的烧录校验来自同一个错误映射，缺少独立物理读取和早期串口，导致在错误前提上继续检查内核。拿最后一条可见日志当作根因，又让定位在 PMU、Hantro 和多核之间来回移动。后来逐层补齐后，还曾把“注册了硬解”“回调说 rendered”“模式名叫 60 Hz”当作过强的成功信号。这些判断都需要更强的独立证据。

操作组织也影响效率：早期每次只改一个参数，我就得再次断电、按 Recovery、下载 RAM Boot，花了很多时间重复操作。回头看，我应该先准备好候选及回滚，完成所有能离线做的检查，再一次进入下载模式完成成组更新和回读；能通过 ADB 或可控软件重启完成的工作，就尽量通过软件完成。但减少重启也不能以牺牲验证为代价，把尚无证据的多项猜测打包成“最终修复”。

### 下次的执行顺序

1. 先建立板型、容量、启动链、恢复通道和串口/ADB 证据，证明实际执行的版本。写入前区分 raw 整盘、Android boot、Rockchip update 和 RAM Loader。
2. 用独立读路径校验地址空间，比较 GPT、IDB 和代码指纹；读取失败先查协议边界，不先宣布坏块。
3. 先得到最小可启动系统，再恢复外设。对自定义 HEVC 这类非必要新驱动设立隔离开关，记录“停用恢复”与“机制已修复”的区别。
4. 对 ARM32 用户空间、BPF/网络、共享内存、图形所有权、音频策略分别验收，不把某一个服务存活当成系统稳定。
5. 视频测试依次确认实际 decoder、像素正确、缓冲交付、最终呈现、真实显示时钟和音画时钟；不让优化掩盖正确性缺陷。
6. 音频把 policy、HAL、ALSA、codec、GPIO、电源和物理接收端分开；“PCM 写成功”和“听到了声音”分别记录。
7. 每次发布记录 source/config/payload SHA、累计补丁、实验撤回项和测试边界。原文件 mtime 不变并不证明没改；隔离输出、运行时替换、持久分区和发布镜像也不能混为同一个版本。
8. 开源时导出最终对应源码，而不是最初 device 目录：本次最终内核相对干净 6.18.60 有 34 项变化，包含此前修正和诊断；只公开最后七个 Hantro 文件会遗漏前面的必要修改。
