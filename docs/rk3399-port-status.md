# Firefly-RK3399 64 位电视系统适配记录

日期：2026-11-08。目标是另一块可以正常启动的原版 Firefly-RK3399，
不是此前排查供电故障的板。继承 RK3288 提交
`4fdb1f9f349b6bf1839e780e3ec5b05cadd6656d` 的电视界面、选台、儿童算术和家长控制。
该提交的 RK3288 实测记录只作为历史依据，不能当成 RK3399 已通过。

## 产品约定

- Android 17 / API 37，ARM64 系统与主要服务，保留 ARM32 应用兼容能力。
- YouTube 使用 Google 官方 Android TV 包 `com.google.android.youtube.tv`，
  保留 Google 签名。禁止用 SmartTube、手机版或换皮客户端冒充官方版。
  安装、游客播放、登录和内容权限分别验收。
- 继承现有电视交互、地区/类型频道分类、3–6 岁算术和家长控制；
  私有频道数据、账号和第三方 APK 不进入公开源码。
- 首版先验证 1080p H.264 与 8 位 VP9；硬件规格上的 4K 能力不能代替
  实际解码、呈现和音画同步测量。AV1、HDR 和 HEVC 不预先宣告可用。
  当前公开能力限制为 H.264 1080p30、VP9 Profile 0 1080p60；这两项均待实测。
  H.264 60 fps 样本用于后续吞吐试验，不能当成系统已经声明或通过的能力。

## 我先排除的跨板误用

| 项目 | RK3399 依据与处理 |
|---|---|
| CPU / ABI | Cortex-A72 + A53，ARM64 内核与用户空间；重新编译 native 库 |
| 原版设备树 | 主线 `rockchip/rk3399-firefly.dtb`，compatible `firefly,firefly-rk3399` |
| 启动链 | RK3399 自己的 TPL/SPL、U-Boot 与 TF-A；不复用 RK3288 Loader |
| 视频 | 主线 rkvdec 提供 H.264/VP9；RK3399 Hantro 的 H.264 被上游禁用 |
| HEVC | 当前固定 6.18.60 rkvdec 不提供这一路；不复制曾导致卡死的定制 HEVC |
| 耳机 | RT5640 + I2S1；不复制 ES8323 混音器控件 |
| HDMI 声音 | 独立简单声卡、PCM0；不沿用 RK3288 的模拟同卡 PCM1 |
| GPU | Mali-T860，Panfrost；不复制 RK3288 特有 NPLL 与时序寄存器补丁 |
| 无线 | RK3399 SDIO 电源和时钟；不复制固定 `ff0d0000` 的 RK3288 恢复脚本 |
| 有线/USB/eMMC | 使用各自 DT 控制器地址，任何写入必须先确认板型及存储目标 |

## 当前验证边界

源码准备、编译、文件结构/ABI检查、真实板启动分别记录。
本轮开始时 Windows ADB 只看到 RK3288，后续检查时没有设备在线。
我没有向现有设备安装或烧录 RK3399 文件。
新板的 eMMC 容量、当前系统、启动日志和全部外设表现尚需接入后读取。

构建目录和输出与旧板隔离。AOSP 基线作为只读 lower，使用独立的可写层和
OUT_DIR；旧 RK3288 out 不作为 ARM64 二进制输入。编译容器资源受限，
不通过全权限容器或改动旧设备树来规避构建问题。

我会在实际结果产生后补充构建工件和校验记录。此前的 RK3288 “通过”结果、
旧镜像时间戳和旧音视频实听不迁移到此板的验收栏。

## 本轮已经完成的准备

- 我已编译并校验 U-Boot v2024.01 + TF-A v2.10 的 eMMC 启动链。
  U-Boot 仅扫描 `mmc0`，不读取旧的持久化环境；这不改变芯片 BootROM 优先级。
- Linux 6.18.60 的 Image、最终 USB2 设备模式 DTB 和六个 Wi-Fi 模块已编译，
  通过架构、配置、版本、符号 CRC 与依赖闭包检查；这仍然不是实机启动结果。
- 我根据真实 Linux 6.18.60 ARM64 头部，将内核加载地址设为 `0x02000000`，
  并让镜像检查覆盖内存跨度，避免只按文件大小判断是否覆盖 ramdisk。
- 我已准备 167 台的个人频道包、完整解析链、离线儿童短片和原六款应用的
  私有构建输入；公开仓库只保留通用功能代码与导入工具。
- 官方 YouTube Android TV 5.30.304 的签名与文件内容已核对，安装流程主机测试
  已通过。版本、签名依据和限制见 [官方 YouTube 集成](rk3399-official-youtube.md)。
- 镜像拒绝错误架构、错误加载地址、内存重叠和未绑定 Loader 的 9 项测试已通过。
  这些是检查程序测试，不是完整镜像验收或板卡启动结果。
- H.264/VP9 后端的四个 FFmpeg 共享库已实际完成 ARM64 构建，架构、SONAME
  和 API 37 链接依赖检查通过。最终安装分区的依赖检查仍需系统构建完成。
- 图形依赖检查器已增加双 ABI 支持，使用真实 Clang 链接的 ARM32 和 ARM64
  样例各通过 16 项检查，包括符号版本、命名空间隔离、APEX 和错误架构拒绝。

完整 Android 分区编译和整盘镜像生成仍在进行。当前没有可宣称已启动的
RK3399 镜像；所有新板上的硬解码、官方 YouTube 播放、音频、网络与输入验收待做。

## 构建中发现的问题与处理

1. 官方 APK 的压缩 JNI 库不能直接通过 AOSP 的已预处理系统 APK 检查。
   我保留原始 Google 签名文件，改为首次开机由 PackageInstaller 安装到数据分区。
2. 原版 RK3399 的 RT5640 有独立的耳机通道开关和左右 DAPM 播放开关。
   我对照上游驱动补齐左右播放路径，避免仅打开通道后仍被静音。
3. 内核默认将 RFKILL、部分红外与 ADC 驱动设为模块。仅带 Wi-Fi 模块会缺依赖。
   我将板卡需要的这些基础驱动内建，并检查每个交付模块的依赖和符号 CRC。
4. AOSP 的一个平台测试模块不能正确处理绝对 `OUT_DIR`，导致全局构建图失败。
   我把同一份独立输出挂到容器标准 `out` 路径，改用相对 `OUT_DIR=out`，
   保留已完成的构建缓存；没有删平台测试或沿用 RK3288 二进制来绕过错误。
5. 上游 USB-C 的角色配置不能仅靠修改 `data-role` 变成可靠的调试口。
   我交叉检查 Type-C、PHY 和 DWC3 驱动后，将首版 USB-C 定为 USB2 设备口，
   用于 ADB；并补齐 Android 对晚出现 UDC 的选择与绑定。连接电脑的实际表现
   仍需新板确认，其他 USB-A 接口用于键盘、鼠标和外设。
6. 旧 BV APK 的一个可选广告库只能供平台指定模块引用，阻断 Android 17 的
   构建图。我只调整 BV 的构建依赖描述，保留其原始 APK、清单与签名；
   应用在新系统上的实际启动和播放仍需实板检查。
